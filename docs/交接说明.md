## 原交接安排（审计结果见上）

用户希望由协作者扩展 Minecraft 版本和加载器范围；尚未确认首批目标组合、公共模块方案或最终支持矩阵。先提交审计和推荐，再让用户决定这些产品与架构取舍。

接手顺序：

1. 用自己的账号在原仓库工作，从最新 `origin/main` 建立 `codex/expand-platform-support` 或其他未占用的任务分支。遵循 [提交与协作规范](../CONTRIBUTING.md)，不创建 Fork 或额外仓库。
2. 阅读 `auth`、`lockdown`、`command`、`ui`、`config` 与数据 Store，列出 Forge/Minecraft API 依赖和可共享纯逻辑；入口顺序见 [项目结构](项目结构.md)。
3. 查官方资料，对 Forge、NeoForge、Fabric 的具体版本组合说明 Java、构建工具、改造范围、维护成本和运行验证需求，记录来源链接与查询日期。
4. 新建兼容性审计文档，推荐一个可独立验证的小范围首批目标；将候选、构建通过、运行通过分别记录。不能仅放宽元数据范围宣称已支持。
5. 将审计推送到原仓库工作分支并创建 PR；后续按已确认范围实施，保留原 Forge 基线、认证限制、原版客户端定位与数据兼容。

这次交接不实施多平台改造，也没有预先确定下一个 Mod 版本号。
