# 文档编写规范

## 目的与范围

让维护者能从文档快速判断功能入口、数据流、配置影响和验证方式。文档描述当前实现时必须以代码为依据；方案或尚未实现的约定必须明确标为“提案”或“未实现”。

## 文档分类

| 类型 | 内容 | 位置 |
|---|---|---|
| 项目入口 | 项目用途、文档导航、快速链接 | `README.md`、`docs/README.md` |
| 使用/运维 | 安装、配置、命令、迁移、备份、故障恢复 | 根目录 `DEPLOY.md` 或 `docs/` 对应专题 |
| 架构/开发 | 模块边界、调用链、数据格式、开发和验证方法 | `docs/` |
| 设计/实施过程 | 有日期的需求方案和实施计划 | `docs/superpowers/specs/`、`docs/superpowers/plans/` |
| 问题记录 | 可复现缺陷、影响、处理状态和修复版本/提交 | `docs/issues/`；问题较少时可先用统一清单 |
| 发布记录 | 每个正式版本的新增、修改、修复和兼容性变化 | 根目录 `CHANGELOG.md`；版本决策和发布步骤见 `docs/版本管理规范.md` |
| 协作与交接 | 分支提交、PR、当前状态、下一步和待验证项 | 根目录 `AGENTS.md`、`CONTRIBUTING.md`，`docs/交接说明.md` |
| 发布操作与材料 | 标签、产物、校验值、Release、回滚和说明模板 | `docs/发布规范.md`、`docs/templates/发布说明模板.md` |

## 写作规则

1. 中文为主，代码标识、命令和配置键保留原文；首次出现的缩写给出解释。
2. 标题描述主题，不用“杂项”“其他”承载多个互不相关的内容。
3. 说明具体对象和操作。命令、路径、配置键、文件名使用反引号；可复制的完整操作用代码块。
4. 讲清前置条件、输入、输出/可见结果、失败情况和权限要求。涉及调用链时按实际顺序写入口到结果。
5. 配置表应包含键、默认值、取值范围（如适用）、作用和生效时机。命令表应包含用法、权限、来源限制（玩家/控制台）和结果。
6. 数据文档说明文件位置、字段含义、兼容/迁移行为、备份和敏感信息边界；不得把密码或密钥示例写成真实值。
7. 每个“已实现”描述应能指向代码、配置或运行方式；不确定的事实标为待核实，不写成承诺。
8. 日期使用 `YYYY-MM-DD`。方案与计划沿用当前日期前缀命名；稳定说明使用固定主题文件名。
9. 同一事实只设一个主维护位置，其他文档链接过去，减少配置与命令清单复制后失同步。
10. “已提交”“已打包”“已打标签”“已公开发行”“已在目标环境验收”分别记录，不相互替代；状态快照写日期和基线提交。

## 缺陷记录模板

```markdown
## [状态] 简短问题标题

- 影响：哪些玩家/服务器/数据会受影响
- 前置条件：版本、配置、权限、操作顺序
- 复现步骤：最少且可重复的步骤
- 预期结果：
- 实际结果：
- 根因/调用链：从入口到错误结果
- 修复范围：涉及模块及明确不涉及的行为
- 验证：执行的检查与结果；未验证项明确列出
- 状态：待复现 / 已确认 / 修复中 / 已修复 / 暂不处理
```

只把已有证据支持的问题标为“已确认”。若当前无法在目标服务器复现，应记录静态分析依据和待现场确认项。

## 变更同步检查

- 玩家可见提示、GUI、行为变化 → 更新相应功能/部署说明。
- 配置项变化 → 更新配置说明及默认值/生效时间。
- 命令、权限变化 → 更新命令表。
- 文件格式、迁移变化 → 更新数据说明、备份步骤和兼容策略。
- 架构边界或主要调用链变化 → 更新 `项目结构.md`。
- 修复缺陷 → 记录复现条件、根因、修复范围和实际验证结果。
- 发布新版本 → 按 [版本管理规范](版本管理规范.md) 更新 `gradle.properties`、`CHANGELOG.md` 和当前部署产物说明。
