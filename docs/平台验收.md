# Minecraft 1.20.1 平台验收

本文保存协作者在 1.3.4 工作分支的原始运行证据与包哈希。1.4.0 的发行构建、附件和验证边界见[发行说明](releases/1.4.0.md)，两批包的版本号与哈希不应混用。

验证日期为 2026-11-19。源码来自原仓库的 `codex/expand-platform-support`。两个测试服各自使用独立目录、世界与合成账号，绑定本机回环地址。分支沿用源码版本 `1.3.4`。[原仓库 PR #1](https://github.com/BrainLeech198/mc_mod.yezong_town_super_toolkit/pull/1) · [兼容性审计](兼容性审计.md)

## 构建、安装与启动

| 组合 | 构建目录、工具与命令 | 安装包 |
|---|---|---|
| Minecraft 1.20.1 / Forge 47.4.0 / 游戏 Java 17 | 根目录，JDK 17，Gradle 8.14.4，ForgeGradle 6.0.54。运行 `./gradlew clean selfTest build --no-daemon` | `build/libs/yzt_super-1.3.4-mc1.20.1-forge.jar` |
| Minecraft 1.20.1 / Fabric Loader 0.20.1 / 游戏 Java 17 | `platforms/fabric-1.20.1/`，JDK 25，Gradle 9.8.2，Loom 1.19.4，以 Java 17 为编译目标。运行 `./gradlew clean build --no-daemon` | 模块的 `build/libs/yzt_super-1.3.4-mc1.20.1-fabric.jar`。服务端另装 Fabric API 0.92.12+1.20.1、Forge Config API Port 8.0.3 Fabric 版 |

Windows 在对应目录执行 `.\gradlew.bat`。Forge 完成 `reobfJar`、`verifyForgeJar` 和 1,482 条自测（0 失败），其中 63 条专门覆盖实际 I/O 故障和重读。Fabric 完成 `remapJar`、`verifyServerJar`，检查最终包中入口、公共类、服务端 Mixin/refmap、语言资源及加载器元数据。最终 Forge、Fabric 包分别含 113、121 个 class，逐一检查均为 Java 17 字节码（major 61），ZIP 无重复条目。两个服务端均使用 JDK 17 启动至 `Done`。

历史 Forge 基线在新环境因固定的本机 JDK 路径无法启动 Gradle。临时覆盖路径和不可达镜像后，原代码可以打包，原自测为 1,412 通过、3 失败。失败项仍期待旧版按钮数与登录提示；已按现有 GUI 的实际入口、按钮动作和引导修正断言。[保存失败和会话修复记录](issues/2026-11-19-写盘故障与认证会话.md)

## 服务端与玩家操作

以下每项使用安装包启动独立服。协议玩家使用 Mineflayer 4.39.0 的 1.20.1 原版协议，用于检查服务端实际收发、多人可见性和重启结果。画面检查另用 Mojang 1.20.1 原版游戏，以键盘鼠标操作；客户端没有安装加载器或 Mod。

| 场景 | 操作与观察 |
|---|---|
| 注册、登录、闸门与超时 | 两端均测新号首进自动打开铁砧、过短留窗、Esc 退出后手动重开、注册落盘、错密后重试、留服登出再次锁定。开启闸门后 OP 也先过闸，错误留窗，成功接账号输入框。一直未登录的玩家在设定时间被断开。 |
| 封锁与解锁 | 同一玩家认证前后分别移动、发送消息、执行受限命令并打开同一个箱子。两端均观察到未认证玩家位置被拉回、命令/聊天受限、箱子不能打开；认证后可以使用箱子。两端还实测未登录时丢弃、拾取和受伤均受限，认证后恢复。 |
| 铁砧与留言 | 两端协议实测先填收件人，再在同一个铁砧填正文，收件人只收到一次通知。打开收件箱详情标记已读，重启后仍保留账号、原信和已读状态。由收件人删除，再次重启确认删除。首次真实画面发现原版客户端会自行清空右槽。修复后两端原版客户端首次打开和键入后均看见绿色按钮。Forge 鼠标点击后登录成功；Fabric 实际按 Esc，重开铁砧并用鼠标提交，注册成功。 |
| 权限与模式 | 两端基础场景中，普通玩家被拒绝进入管理命令，OP 可以查风险记录。Forge 未安装 LuckPerms 时，OP2 能查状态，修改闸门被拒；OP4 需通过本人二次验密才能改闸。退出时记录创造模式，再次认证后恢复创造及其能力。两端均在首次模式强制为生存的情况下，以创造、旁观、冒险、生存四种模式退出再登录，核对恢复后的模式和对应原版能力包。 |
| 可选 LuckPerms 5.4.102 | 两个最终包均在对应加载器上完成 7 项实测。未设置节点的普通玩家被拒；明确授予管理后可管理；闸门节点独立允许或拒绝，允许时仍需二次验密；明确拒绝对 OP4 同样生效；撤销节点设置后恢复原 OP 门槛。另在只装工具箱的最终 Forge 服再次通过普通玩家、OP4 管理与改闸验密三项。 |
| 称号与广播 | 两端实测授予并佩戴后称号持久化、认证玩家聊天前缀可见，喊话能送达另一玩家并按冷却限制重复发送。两端均以两名玩家确认佩戴、重定义（含颜色）、删除称号定义时双方收到 Tab 变更。 |
| 写盘失败与锁定 | Forge 和 Fabric 真服均令合成账号库临时文件不能创建，注册、正确登录和错密均返回存储失败，账号记录原样，玩家保持锁定；移除故障后可重试成功。连续 4 次错密触发 90 秒锁定，重启保留，到期后登录并清零。 |
| 配置与来源地址 | 现有 Fabric 测试世界缺少该 TOML 时，使用含 14 秒超时的模板初始化世界配置；全局同名配置为 45 秒；按 14 秒超时。将世界配置热改为 20 秒，随后人为写坏测试 TOML，观察到仍按上次有效值超时。在无地址适配器的 `auto` 模式下，从两个临时源端口登录均记录同一回环 IP。Fabric 最终包另加载合成可信适配器，在 `auto` 和旧 `header` 下首个回调返回空、第二个返回有效地址后停止，`remote` 使用连接地址且未调用适配器。 |

**证据与包版本。** 注册/闸门、收信及两轮重启使用了多个迭代包。原版右槽修复、账号库写失败和跨重启错密锁定先在 Forge `27fe5b64…8f5d67` 和 Fabric `0755b5ea…3228c8b` 进行。最后一次仅修改共用的 LuckPerms 权限查询。上表给出最新两包的完整哈希，已在最终包单独完成权限实测；Fabric 的四种模式、五库对照和合成代理也在最终包复核。随后移除所有测试用可选组件：仅装工具箱的最终 Forge 服、仅装工具箱与两个必需依赖的最终 Fabric 服，均由 Mojang 原版 1.20.1 客户端看见首次铁砧、实际键入并点击右槽，看到登录成功及游戏世界。最终 Fabric 包也以同一收件人经过第二次重启，用铁砧登录并打开收件箱，确认此前删除的同一封信仍不存在。

### 运行中发现并修正的差异

- **铁砧右槽。** 协议玩家可以读到右槽物品并提交，实际原版画面却显示红叉。原版在接收左槽和改名时重新计算配方。服务端现在等待一 tick，再向仍在当前窗口的同一连接同步右槽；输入文字与光标继续由原版处理。
- **称号。** Forge 原先只给佩戴者发送玩家信息，旁观者未收到更新。现在通过 Forge 的显示名/Tab 刷新入口，将佩戴、改定义、删除定义的变化传给其他玩家。
- **世界配置。** 在 Fabric 的初次验证中，全局 45 秒超时覆盖了已有世界的 14 秒设置。Fabric 现在绑定实际世界文件，检测编辑器替换文件后的修改，坏配置保留上次有效值。
- **可选权限。** 原反射代码从静态 provider 查实例方法，并查找了错误的缓存数据与三态类型。共享权限实现现在沿 LuckPerms 公开方法的返回类型读取，逐项区分显式允许、显式拒绝和未设置；未设置使用该节点原有 OP 等级。

## 复验方法

1. 分别使用匹配加载器的全新 1.20.1 服务端和同版本原版客户端。将本表的最终 JAR 放入对应 `mods/`，按平台补足依赖并记录哈希。使用两个合成玩家 A、B，普通玩家、管理员和控制台分别检查。可使用 `level-name` 指向独立测试世界。
2. A 首次进服先试走动、发言、开箱和执行需要登录的命令。输入过短密码点击右槽，确认文字仍在，按 Esc，手动重开并输入有效密码。B 观察注册前后可见性。留服登出，尝试错误再正确登录。启用闸门后让普通玩家和 OP 重连，分别检查闸门、登录和超时。输入仅使用测试值。
3. A 在写信面板选手输收件人，在同一铁砧分两步提交。B 进入 `/yzts mail manage` 查看详情。服务端正常 `stop` 后重新启动，核对已读和内容。删除该信，再重启确认。取消写信或保存失败时检查 B 没有收到新信。
4. 在临时账号库旁新建名为 `users.json.tmp` 的空目录，让注册或登录产生正常 I/O 错误。比较操作前后 JSON、内存所见及重启结果。移除该空目录后使用同一输入重试。另用测试副本检查坏 JSON 以及五库的备份保护。[五库存储故障用例](../src/selftest/java/com/yztc/auth/selftest/StoreFailureChecks.java)
5. 依次以生存、创造、冒险、旁观退出，在玩家离线后让下次进入时的初始模式与保存值不同，认证后核对模式与能力。将 `restoreLastGameMode` 设为 false，重复操作，核对按配置保留当前模式。称号回归使用第二个已登录玩家观察聊天、Tab 和原版队伍，普通/管理员分别发送公告和喊话。
6. 选装对应加载器的 LuckPerms 5.4.102，先以非 OP 运行 `/yzts admin status`。由控制台对测试玩家设置/清除 `yzt_super.admin` 和 `yzt_super.gate` 两个权限节点，将节点分别置为 true、false 或 unset，重连刷新命令树。对普通玩家和 OP4 重复查状态、改闸与取消二次验密，最后撤销合成账号的节点和 OP。
7. 实际部署可信代理时，由适配器验证代理来源及转发信息。在 `auto`、旧 `header` 和 `remote` 三种模式中，分别检查确切地址与回退。同一主机换临时端口重新登录，核对持久化地址不含端口。限流键和地址变更提醒的联动可在实际代理环境继续复验。[代理适配契约](代理IP适配.md)

## 数据、平台限制与待实测范围

账号、留言、位置、称号和风险仍写入原有的 `config/yzt_super/` 五个 JSON 库。世界配置仍取 `<世界>/serverconfig/yzt_super-server.toml`。跨加载器检查使用 Forge 产生的非空合成五库副本（5 个账号、6 条位置、1 封私信、1 份称号归属、5 条风险）。逐文件核对副本哈希后，在最终 Fabric 服务端初始化的配置环境用对应 Store 加载并向独立副本回写，五个完整 JSON 树逐字段相同。此分支无需数据格式迁移。停服后保存世界、配置及原加载器的完整同一时点副本，切换只在副本上测试，回滚时恢复相应副本。整库解析失败时暂停该库写入，保全原件和 `.bak`。旧格式将缺失或纯空白文件视作空库；若怀疑存量文件被截断为零字节，应先停服并从独立备份核对。[部署与回滚](../DEPLOY.md)

Fabric 对没有原版队伍的玩家使用仅发给客户端的显示队伍呈现头顶称号。已有真实队伍时保留真实队伍的头顶前缀、配色和碰撞设置，工具箱称号继续用于聊天和 Tab。复杂整合包的第三方队伍改写、实际公网代理链路、第三方 Mod 之间的命令/事件竞争仍待实测。`restoreLastGameMode=false`、多人 AFK 广播、管理员 45 人以上分页和指南书逐页显示等长尾组合待实测。另见[旧版本完整走查清单](../DEPLOY.md#9-历史完整验收清单)。NeoForge 1.21.1 属于后续计划。
