# Minecraft 版本与 Mod 加载器兼容性审计

查询日期为 2026-11-19。审计对象是原仓库 [main 的 53ed590](https://github.com/BrainLeech198/mc_mod.yezong_town_super_toolkit/tree/53ed590e5e5e401b76898eb50e5150d9548c1160)，Mod 版本为 `1.3.4`。本文记录源码、历史构建证据和待决定的实施方案。服主可安装的组合与验证状态见[首页矩阵](../README.md#适用范围)。

这是一阶段审计快照。用户随后确认 B–E；当前构建方式、依赖和验收结果见[平台验收记录](平台验收.md)。

**建议先保留 Forge 1.20.1 作为对照，在同一游戏版本验证 Fabric 的全局命令封锁和首次铁砧输入。** 这一步可以为已有 1.20.1 世界增加加载器选择，并能单独定位加载器差异。通过后再用 NeoForge 1.21.1 增加一个游戏版本。仓库没有服主装机分布数据，排序依据是兼容收益、一次改变的变量数和每个组合要承担的回归工作量。

gradle selfTest --no-daemon --console=plain

## 2. 现有依赖落在哪里

源码路径均相对 [com.yztc.auth](../src/main/java/com/yztc/auth)。同一包内可能同时包含可复用算法和平台调用。

| 功能 | 定位与调用链 | 可共享内容与适配边界 |
|---|---|---|
| 入口、路径、生命周期 | `YzAuthMod` → 注册 SERVER 配置、加载 users、创建各 Store、绑定认证服务和事件。随后 `auth/AuthEvents.onServerStarted` 读取 mail、lastseen、risk、titles。`onRegisterCommands` 接收本次 dispatcher | 各平台提供 config/game/world 路径与运行期装配。世界配置可读后再载入依赖过期设置的留言。重载命令树、停服再启动时检查静态 Holder 与监听器生命周期 |
| 认证、封锁 | `AuthEvents.onLogin → AuthManager.onJoin` 建立 PendingState 并安排下一 tick 打开 `AuthGui`；同一个进服回调随即执行 `LockdownSync.lock`，实际开窗在后。服务端玩家 tick 的 END 阶段处理超时、位置回拉或已登录挂机；`lockdown/LockdownHandler` 同时处理命令、右键、破放、攻击与受伤、丢拾、聊天 | `RateLimiter`、密码算法、白名单判定可以单测。玩家对象、取消语义、tick 阶段、连接与原版同步包须在各平台实现。Forge 全局命令的控制点在执行前，范围包括别的 Mod |
| 命令与权限 | `command/RootCommand`、`BareCommands` 与 `AdminCommands` 接 Brigadier 和 `CommandSourceStack`；`perm/Permissions` 查询可选 LuckPerms，否则走 OP 等级；GUI 的管理入口也需验证权限 | 命令名、参数、来源、权限节点及反馈保持一致。普通管理默认 OP2，闸门 OP4。游戏内危险操作检查本人的二次确认规则，控制台有自己的路径。命令注册时机及 LuckPerms 适配由平台负责 |
| 原版菜单和文字输入 | `ui/AuthGui` 把账号提交交给 `RootCommand`，`InputPrompt.choose` 负责关闭旧菜单并提供铁砧/命令输入选择；`ButtonPanel`、`AnvilInput.CaptureAnvilMenu`、`UiSession`、`Defer` 维护原版箱子/铁砧、槽位、延迟及取消；`MailPanel`、`AccountPanel` 接多步回调 | 共享每步意图与结果。菜单类型、物品、重命名同步、容器 id、结果槽、断线和下一 tick 回调属于游戏/平台。首次打开须在客户端就绪后；输入过程中不能提交；仅点结果槽提交一次 |
| 玩家状态与展示 | `AuthManager.completeAuth → LockdownSync.authenticate → restoreLastGameMode`，另有 `TabHider`、`TitleEvents`、`BroadcastCommand/Broadcaster`、`Lang/ServerLang`、`BookGuide`；`AuthEvents.onLogout → recordLastSeen → UiSession.forget → onLeave` | 能力、背包、Tab、显示名、聊天/标题、游戏模式、传送和指南书依赖 MC API 或具体包。字宽、文案资源、冷却规则可复用。区分已认证、留服登出、真正断线和超时踢出 |
| 连接地址 | `AuthManager.resolveIp`、`api/ClientIpResolveEvent`。`auth/HeaderProbe` 是为兼容保留的空实现。auto/旧 header 同步请求可信服务端适配器，首个有效 `InetAddress` 生效；remote 直接取连接，对端地址去临时端口 | 保留现有 Forge 公共事件及签名，为新平台提供对应回调。适配器验证来源；无结果回退到连接。限流、审计、IP 变更提醒共用归一化地址。[代理契约](代理IP适配.md) |
| 配置与存储 | `config/AuthConfig` 基于 ForgeConfigSpec；`FMLPaths.CONFIGDIR/yzt_super` 下五库，审计在 `GAMEDIR/logs/yzt_super-audit.log`；SERVER TOML 位于 `<world>/serverconfig/yzt_super-server.toml` | `security/PasswordHasher`、数据模型、`AccountStore`、`LastSeenStore`、`RiskStore`、`title/TitleStore` 的 Path/NIO/Gson 读写可复用。`MailStore.pruneExpired` 直接读取 `AuthConfig.mailExpireDays()`，先显式传入过期策略。静态服务与含 `ServerPlayer` 的类暂留平台层 |

**历史修复必须保留。** 首次进服推迟一 tick 打开铁砧，新玩家获知首次设密与最低长度，老玩家收到登录和忘密指引。认证输入失败留窗重试；留言或公告发送失败保留正文，Esc 取消，下一步骤清空输入并沿用窗口。已落盘才报告注册成功。改密、改邮箱、管理改号/闸门、留言发送/已读/删除和称号写失败已有回滚分支。留言加载按条隔离坏记录、归一化名字。验证须覆盖 GUI 与命令两条入口。[首开记录](issues/2026-11-15-首次进服铁砧输入无响应.md) · [留言与铁砧](issues/2026-11-18-留言保存与铁砧重试.md) · [认证与留言数据边界](issues/2026-11-18-认证与留言数据边界.md)

**现存写入缺口会影响移植验收。** [AuthManager.login](../src/main/java/com/yztc/auth/auth/AuthManager.java) 的错密计数/锁定、成功登录/旧哈希升级均忽略 `persist()` 返回值，成功路径仍会放行。[退出快照](../src/main/java/com/yztc/auth/auth/AuthEvents.java) 先更新内存再写盘；[风险面板](../src/main/java/com/yztc/auth/ui/RiskPanel.java) 保存异常后仍会提示处理成功。`RiskCommand`、`RiskLog` 和实际执行的 `MigrateCommand` 也涉及先改内存再保存。各库读取整个损坏文件时须检查后续保存是否保全原件；`MailStore.save` 写前清过期项，也需要覆盖失败后的内存视图。上述是静态发现，磁盘故障与重启均待实测。建议先在 Forge 对照环境用合成数据独立修复、验证，再复用相关实现。

## 3. 候选组合与顺序

每行固定一个可试验的组合。各平台自己的官方模板用于确定工具链，最终还需将精确依赖、Wrapper 校验和和构建提交记录在该平台。JDK 一栏区分运行服务器与启动 Gradle。改造/维护成本是本仓库的相对估计。

| 顺序与状态 | Minecraft / 加载器 | JDK 与构建工具 | 改造 / 持续维护 | 单独的实机重点 |
|---|---|---|---|---|
| 对照，历史构建通过、待运行验证 | 1.20.1 / Forge 47.4.0 | 运行及构建 17；Gradle 8.14.4、ForgeGradle 6.0.54、reobfJar | 低 / 每次复跑既有行为 | 原版客户端首开与错密锁定、留服登出、权限、旧库与写失败 |
| 首个新增候选，计划支持（待确认） | 1.20.1 / Fabric Loader 0.20.1 + Fabric API 0.92.12+1.20.1 | 游戏与目标字节码 17；按模板用 JDK 25 运行 Gradle 9.8.2；建议试配稳定 Loom 1.19.4、official mappings、remapJar | 中高 / 每次复测全局命令、输入与事件覆盖 | 同一份合成世界的副本对照 Forge。先验证未认证拦截所有命令、重新登录与原版铁砧 |
| 第二个新增候选，计划支持（待确认） | 1.21.1 / NeoForge 21.1.267 | 运行及构建 21；官方 MDK 用 ModDevGradle 2.0.148、Gradle 9.2.1 | 高 / 新游戏版本的 API 与新加载器需各自跟踪 | 配置时序、数据组件化的物品与书、玩家包、游戏模式、原版连接与升级副本 |
| 后续评估 | 1.21.1 / Fabric Loader 0.20.1 + Fabric API 0.116.18+1.21.1 | 游戏与字节码 21；模板同代 Gradle 9.8.2，候选构建 JDK 25、Loom 1.19.4 | 已有 Fabric 后为中 / 仍多一套固定版本与实机回归 | 复查执行前命令钩子、容器与聊天包，1.20.1 的结果不能沿用 |
| 按部署需求评估 | 1.21.1 / Forge 52.1.20 | 游戏与字节码 21；发行 MDK 的 Gradle 9.3.1、ForgeGradle `[7.0.3,8)`，实施时钉住实测补丁版本 | 中高 / 额外维护一套 Forge 主版本 | 与 NeoForge 分服验证事件取消、世界配置、铁砧及重映射后的最终包 |

## 4. 构建和源码如何组织（提案）

| 方案 | 优点 | 长期代价与取舍 |
|---|---|---|
| 每个平台完整复制项目 | 首次试验容易撤销，能直接采用各自的官方工具链 | 登录修复、存储回滚和双语文案需多处同步。只适合短期探针 |
| 独立平台构建，按需共用一个 Java 源码模块（推荐） | 根项目保留 Forge 入口与任务，新平台可单独构建。首次只抽取第二个平台确实需要的规则 | 独立 Wrapper、依赖与服务端测试矩阵需要维护。JDK 17 公共代码可供 21 使用，版本特有 API 留在对应模块 |
| 统一根构建和跨加载器框架，集中封装游戏对象 | 平台轮廓稳定以后能减少部分重复装配 | 目前 Forge、Loom 和 ModDevGradle 使用不同 Gradle/JVM；强行统一会同时改变老平台的构建和行为。尤其不能靠一个通用“登录事件”推断事件先后与取消语义 |

保留根目录 Forge 构建入口。新增 `common/`（Java library，目标 17），以及独立构建目录 `platforms/fabric-1.20.1/`；进入下一阶段时才增加 `platforms/neoforge-1.21.1/`。各构建将同一份 common 源码作为 Java 子项目引入，并将其编译输出和必要资源打入最终平台 JAR 一次，服主只安装对应平台产物与声明的服务端依赖。避免要求本机先 `publishToMavenLocal`，也避免加载另一平台的类。只在出现两个调用方时抽出纯规则。保留 Forge 的 `@Mod` 入口、SERVER 配置、全局事件和对外地址事件。精确的 MC 类型只在同游戏版本、同映射且已证明可共用时共享。

Fabric 使用 `fabric.mod.json` 的服务端 entrypoint（`DedicatedServerModInitializer`）和 `environment: "server"`，声明 Loader、Fabric API、游戏及 Java 版本。实现世界级配置读取，沿用键、默认值、配置范围、启用时机和原 TOML 路径。NeoForge 使用 `@Mod`、匹配 MDK 的配置/事件总线和 `META-INF/neoforge.mods.toml`。三端各自实现原版 GUI/包，保持 `yzt_super` 命名空间、中英文语言键与服务端可见的兜底文本。按 MC 调整 `pack.mcmeta`（当前为 15）与物品/书页的表示。对最终 JAR 检查平台入口和元数据，确认其不会意外加载客户端专有类。[Fabric 项目结构](https://docs.fabricmc.net/develop/getting-started/project-structure) · [NeoForge Mod 文件](https://docs.neoforged.net/docs/1.21.1/gettingstarted/modfiles/)

统一从根 `gradle.properties` 读取 `mod_version`。建议发行文件名为 `yzt_super-<Mod版本>-mc<游戏版本>-<forge|fabric|neoforge>.jar`，例如 `yzt_super-<Mod版本>-mc1.20.1-fabric.jar`。Loader 的精确测试版本和 SHA-256 随附件清单记录。保持现有根项目构建命令可用，切换命名时同步更新部署说明。Forge 交付 reobf 后的包，Fabric 交付 remap 后的包，NeoForge 按所选 MDK 的发行任务检查产物。共用版本号但按平台分别打包、验收与发布；文档阶段沿用 1.3.4。正式版本由发布负责人按实际兼容影响确定。[版本管理规范](版本管理规范.md) · [发布操作规范](发布规范.md)

每个单元开工前记录玩家动作、入口、输入/输出、写入边界和文件范围。结束后附最小差异、基线和源提交、精确工具版本、命令、产物及哈希、自测/启动/试玩三层证据。未完成的用例逐项写“待实测”。只有必要的游戏/加载器/平台 API 依赖装在测试服务端，测试客户端始终保留一份同版本、无 Mod 的原版安装。

## 6. 数据兼容与可复现验收

现阶段及建议首批均沿用 `config/yzt_super/`。账号库 `users.json` 默认 v1、包含闸门与账号，保留旧哈希读取以及成功落盘后的升级。留言 `mail.json` v1 保留 id、收发人和已读时间；位置 `lastseen.json` 兼容旧记录缺失 gameMode，现有保存格式 v2。称号 `titles.json` v1 含定义和玩家选择，风险 `risk.json` v1 含记录与处理状态。审计日志继续只记必要的结果。各 Store 写同目录临时文件，复制已有文件为滚动备份，再用原子替换或文件系统支持的后备替换。单个 `.bak` 不能还原多个文件在同一时刻的状态。

用虚构账号准备中英两套提示、旧版数据和两个独立测试目录。停服备份完整世界（含 serverconfig）、config、mods 和原运行版本；在副本上跑各平台，以条目/字段语义和重启结果比较。两个服务端不得同时写同一个库。如果某平台确实需要改格式，先单列版本读取分支、幂等迁移/试跑、备份与旧服回读的范围，经确认再更改。跨 MC 升级的回滚须恢复升级前的世界、配置、原 JAR 和对应加载器。仅改回 JAR 不能回滚世界升级。

| 待实测场景（每个组合单独执行） | 玩家操作与判定 |
|---|---|
| 启动与原版连接 | 从空服装最终 JAR 和声明的服务端依赖，记录 Loader/JDK/启动到 Done。两名同版本原版客户端进入；观察聊天兜底语言、无需额外下载、显示名与 Tab 隐藏/恢复 |
| 注册、闸门、错密和超时 | 新账号首开铁砧能键入，设置密码并获知下次登录方式。开启闸门后，管理员也先过闸；错密仍受限，锁定跨重启、到期后可登录。同一连接地址重连仍按同一限流键。等待超时、主动退服、留服登出、快速重连，确认清理会话且不会触发旧菜单 |
| 封锁与解锁 | 入服时观察移动回拉、建造/使用、双方伤害、丢拾、聊天。分别测裸认证命令、`/yzts gate`、`/yzts login`、`/yzts register`、`/yzts help` 这些白名单入口，以及原版、其他 Mod 的无害命令。闸门前后都要检查认证限制。用计数或可见世界状态核对服务端是否执行。认证后复做；留服登出再查能力、背包和 Tab 同步 |
| 铁砧生命周期 | 首次键入、单击结果、重复点击、Esc 及断线，核对每次回调次数、占位物品清理。错误密码可重输；改密/邮箱多步在同窗切换，取消无副作用；发送失败时正文仍在 |
| 留言和重启 | A 给离线 B 发私信，B 登录查收件箱和详情，已读、删除、公开板、权限分别复核；每次重启读回。用混合大小写名字、坏单条与同一封信重复提交做对照。发送失败时 B 无通知，恢复写权限后原正文只发一次 |
| 权限、游戏模式与其他功能 | 普通玩家、OP2、OP4、LuckPerms 显式允许/拒绝和控制台分别执行管理与改闸；核对游戏内二次确认、取消和越权拒绝。四种原版模式分别退出再登录，另测无旧值/关闭恢复时保持服务器模式。核对位置与传送、风险标记、称号可见性、公告、挂机与喊话冷却 |
| 可信地址与数据失败 | 有/无可信代理适配器分别登录；auto/旧 header 首个可信地址生效，remote 或无人提供时走连接回退。对测试库临时阻止新临时文件写入，依次试注册/登录、留言、称号、风险及下线保存；比较提示、内存和重启后记录，恢复可写后重试。整份坏 JSON 另用副本，确认故障可见、原文件仍可恢复 |

已有 [SelfTestMain](../src/selftest/java/com/yztc/auth/selftest/SelfTestMain.java) 覆盖哈希、限流、白名单、Store 往返、UiSession 等，也初始化 Forge 配置并检查 Forge 元数据。先保留原任务，再把真正不依赖游戏类的断言复用于平台构建。补充混合大小写、坏单条和写失败后的回读。完整服主用例见[部署验收表](../DEPLOY.md)。报告填入源提交、组合、最终 JAR 哈希、每项结果与未覆盖条件，生产数据和敏感日志不进入仓库。

**待决定的范围**　建议批准 B–E，即 Forge 1.20.1 对照和 Fabric 1.20.1 首批，采用独立构建、最小 common。D 可以独立审查和停止；只有 E 验收完成才建议发布 Fabric 包。F 为后续推荐，开始前再确认实际服务器目标。
