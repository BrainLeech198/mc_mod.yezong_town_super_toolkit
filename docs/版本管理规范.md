# 版本管理规范

## 版本格式

Mod 使用 `主版本.次版本.修订号` 三段数字版本，例如 `1.2.3`。每个正式发布版本必须高于上一个正式发布版本；已发布的版本号不重复使用。

| 变更类型 | 递增方式 | 判断依据 | 示例 |
|---|---|---|---|
| 修复缺陷、文案修正、兼容的体验优化 | 修订号 +1 | 现有配置、数据、命令和集成方式继续兼容 | `1.0.0` → `1.0.1` |
| 增加向后兼容的功能或扩展点 | 次版本 +1，修订号归零 | 旧配置和旧数据仍可使用，原有入口仍有效 | `1.0.1` → `1.1.0` |
| 移除/改变既有功能，或造成配置、数据、命令、权限、API 不兼容 | 主版本 +1，其余归零 | 使用方需要迁移、改配置或修改集成代码 | `1.4.2` → `2.0.0` |

不能仅因改动文件多就提高主版本；按对服务器配置、持久化数据、命令使用者和适配器的兼容影响判断。无法确认兼容性时，先记录影响与迁移步骤，再确定版本级别。

## 唯一版本来源

- `gradle.properties` 中的 `mod_version` 是 Mod 发布版本的唯一维护入口。
- `processResources` 会把它写入 `mods.toml`；Gradle 也用它生成 JAR 文件名和 manifest。不要在这些生成结果里手工维护另一份 Mod 版本。
- `minecraft_version`、`forge_version` 和对应范围是运行平台兼容目标，不属于 Mod 发布版本号。改变它们不自动意味着 Mod 主版本变化，应另行按兼容影响判断。
- 账号、留言等 JSON 内的 `version` 是各自数据格式版本，独立于 Mod 版本。修改持久化格式时，必须设计兼容读取/迁移并更新对应数据说明。

输入到产物的关系示例：

```text
gradle.properties: mod_version=1.1.0
    -> mods.toml: version="1.1.0"
    -> build/libs/yzt_super-1.1.0.jar
    -> JAR manifest: Implementation-Version=1.1.0
```

## 发布记录

- 每次发布在根目录 `CHANGELOG.md` 增加对应版本条目，按“新增 / 修改 / 修复 / 兼容性”记录用户可见变化。
- 条目只写本次实际进入产物的改动；未完成或尚未验证的内容明确标记，不写成已发布能力。
- 发布版本、产物文件名和部署说明中的版本必须一致。问题记录应链接或标明对应修复版本。

## 打包清单

1. 根据本规范确定版本级别，在 `gradle.properties` 更新 `mod_version`。
2. 更新 `CHANGELOG.md` 和涉及的部署/配置/命令文档；搜索旧产物名，清理当前说明中的过期引用。
3. 执行项目的 Gradle 打包任务。ForgeGradle 的 `jar` 任务会继续运行 `reobfJar`，应交付重映射后的 JAR。
4. 检查 `build/libs/` 中 JAR 文件名、修改时间和大小；确认 JAR 内的 `META-INF/mods.toml` 与 manifest 使用新版本。
5. 记录最终产物路径和 SHA-256。实际服务器体验仍需在目标环境验收。
